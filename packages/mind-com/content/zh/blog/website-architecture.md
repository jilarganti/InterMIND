# Mind.com 网站构建解析：Nuxt 4 架构

<img src="/blog/iStock-681469612.jpg" alt="Mind.com 架构" width="500" align="right" style="padding: 1.5rem"/>

这是对 [mind.com](https://mind.com) 实际构建方式以及我们做出这些选择的原因的详细解读。这是一个营销网站——包含落地页、博客、法律页面和联系表单——因此有趣之处不在于任何单一的技术。而在于我们划定的界限：什么在服务器上渲染，什么传输到浏览器，什么作为构建时脚本保留。如果某个决定是权衡的结果而非显而易见的优势，我们会如实说明。

该网站是 pnpm monorepo（代码库名为 `InterMIND`）中的一个包。它运行在 **Nuxt 4** 上并部署到 Vercel。这里没有任何奇特之处；价值在于各部分之间的契合。

## 为什么选择 Nuxt 4 和 SSR，而不是静态构建

营销网站可以是纯静态输出。但我们选择在服务器上渲染，使用 Nuxt 的 Nitro 引擎和 `vercel` 预设，其原因具体而非空泛。

我们有一个提交到后端的联系表单，跨七种语言的每个区域路由，以及频繁更新的内容，以至于我们不想考虑哪些页面已过时。SSR 允许一个代码库处理营销页面、本地化路由和表单端点，而无需将单独的服务附加到静态包上。Nitro 在构建时将服务器编译成 Vercel 函数，因此我们无需运行或维护自己的服务器即可获得服务器渲染。

权衡是坦诚的：SSR 意味着存在请求时的工作，而纯静态网站则没有。对于这个规模的网站，这种成本很小，作为交换，我们避免了将静态前端与独立 API 拼接在一起的协调问题。如果这是一个没有动态表面的万页文档网站，静态生成会是更好的选择。但它不是，所以 SSR 获胜。

## 内容：@nuxt/content 和 MDC

博客和法律内容是 `content/blog/` 和 `content/legal/` 下的 Markdown 文件。我们使用 **@nuxt/content v3**，它在构建时将这些文件解析到本地的 better-sqlite3 数据库中，并允许我们像查询数据一样查询它们。通过 `content.config.ts` 中的 Zod 模式强制执行 Frontmatter 结构，因此缺少 `title` 或 `date` 格式错误的帖子会在构建时失败，而不是发布损坏的内容。

博客采用 **MDC** 编写——带组件的 Markdown。提示框是 `:::tip{title="..."}` 而不是原始 HTML，这保持了源代码的可读性，并允许我们在一个地方（`ProseTip` 组件）控制渲染，而不是将标记散布到每个帖子中。

将内容作为文件保存在仓库中意味着它可以进行版本控制，在拉取请求中进行审查，并且可进行差异比较。没有单独的 CMS 需要登录，也没有数据库需要备份。其局限性在于：编辑需要提交，因此这适合已经习惯使用 Git 的团队，而不适合大型的非技术编辑人员。

## 国际化与翻译工作原理

该网站通过 **@nuxtjs/i18n** 和 `prefix_except_default` 策略支持七种语言环境——英语、西班牙语、葡萄牙语、法语、德语、俄语和中文。英语从根目录提供服务；其他每种语言环境都位于其自己的路径前缀下。UI 字符串位于 `app/locales/<code>.json` 中。

翻译是一项双轨工作，我们将其轨迹分开。UI 字符串和内容由两个 Node 脚本——`scripts/i18n-translate-ui.ts` 和 `scripts/i18n-translate-content.ts`——进行翻译，它们基于 AI SDK 和 Anthropic 模型构建。这些脚本作为构建时创作步骤运行，而非请求时：由人工触发它们，审查输出，然后提交。翻译结果是仓库中的普通文件，与其他所有文件一样。

这是我们刻意划定的界限。没有运行时翻译，也没有访问者加载页面时进行即时语言模型调用。翻译是预先生成的，并作为普通的本地化路由提供，这使得渲染可预测，并允许我们在发布前进行校对。

## 设计系统：Tailwind v4 和 @nuxt/ui

样式采用 **Tailwind CSS v4** 并结合 **@nuxt/ui v4**。新访问者默认进入深色模式；页面背景是刻意的近黑色，`#0a0b0d`，而不是纯黑色。每个页面和组件都构建为在浅色和深色模式下都能工作——这是我们坚持的约束，而非事后考虑，因此没有硬编码仅适用于浅色模式的颜色。

依赖 @nuxt/ui 意味着我们继承了可访问、一致的组件，而不是从头开始重新构建按钮、表单控件和叠加层。代价是我们需要遵循一个依赖项的约定，而不是一个完全定制的系统，对于营销网站来说，这是这种权衡的正确一面。

## 后端：Nitro 服务器路由和 Pipedrive

后端很小，与项目同存，作为 `server/` 下的 Nitro 服务器路由：

- `server/api/submit-form.post.ts` 处理联系表单。
- `server/api/health.get.ts` 是健康检查。
- `server/api/__sitemap__/urls.ts` 提供站点地图。
- `server/routes/llms.txt.ts` 和 `llms-full.txt.ts` 为 AI 爬虫提供机器可读的摘要。
- `server/middleware/` 包含横切逻辑，包括用于已停用 URL 的 410-gone 处理器和受众处理。

当有人提交联系表单时，潜在客户会通过 `server/utils/pipedrive.ts` 发送到 **Pipedrive**，该文件会创建一个人员和一条潜在客户记录。这是唯一的 CRM 集成，也是表单数据唯一去向。其间没有队列、数据管道或对象存储——端点验证输入并调用一个 API。保持如此直接意味着几乎没有什么会出错，并且当出现问题时也无需过多推敲。

此外，营销网站上刻意没有用户认证功能。它是一个宣传册和联系表单，而不是一个应用程序；增加登录和会话功能只会增加我们需要保护的攻击面，而没有任何益处。

## 可观测性：Sentry 和 PostHog，带有同意门控

我们运行两个可观测性工具，它们扮演着不同的角色。

**Sentry** (`@sentry/nuxt`) 捕获错误。它以构建时模块的形式接入，并在开发环境中保持关闭，以避免本地噪音干扰。它的作用是在生产环境中出现问题时通知我们。

**PostHog** (`nuxt-posthog`) 处理产品分析，其围绕同意的行为值得详细说明。它默认是**选择退出**状态。网站不显示 cookie 横幅：对于来自欧洲经济区、英国或瑞士的访问者，分析功能保持关闭；对于其他所有人，`app/plugins/posthog-consent.client.ts` 会启用它。默认情况下不进行跟踪；仅在无需同意的情况下才启用。PostHog 覆盖分析，Sentry 覆盖错误——这就是全貌，没有单独的标签管理器或第三方分析层。

## SEO 和 AI 爬虫

SEO 由 `@nuxtjs/sitemap` 和 `@nuxtjs/robots` 负责站点地图和 robots 指令。重定向和缓存头——包括网站积累的遗留 URL 重定向长列表——都存储在 `vercel.json` 中，紧邻它们在边缘生效的位置。

上述提到的 `llms.txt` 和 `llms-full.txt` 路由是对当前网页阅读方式的致敬：它们为 AI 爬虫提供了清晰、结构化的网站摘要，而不是让它们抓取渲染后的页面。这种方式服务成本低廉，并且意味着读取网站的机器能够获得准确的版本。

## 部署

一切都部署到 **Vercel**。Nitro 的 `vercel` 预设将服务器路由转换为 Vercel 函数，将页面转换为服务器渲染输出，因此 `git push` 变成了部署，无需维护单独的构建和发布管道。作为 pnpm monorepo 的一部分，mind.com 与其他包共享工具和锁文件管理，同时保持独立部署。

## 总结

这些都并不罕见，这正是重点。Nuxt 4 让我们无需运行服务器即可实现 SSR；@nuxt/content 将帖子和法律页面作为可审查的文件保存；i18n 和翻译脚本将网站本地化为一个可供我们校对的构建步骤；精简的 Nitro 后端将潜在客户转交给 Pipedrive；Sentry 和 PostHog 监控故障和行为，并在需要同意的情况下关闭分析。

网站之所以易于理解，是因为我们减少了活动部件的数量，并让每个部件都各司其职。对于一个营销网站而言，平淡易读永远胜过花哨巧妙。
